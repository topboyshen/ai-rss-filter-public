# 隔离切换控制器的崩溃恢复诊断

这不是生产切换适配器或部署授权。`durable_handoff_cutover.py` 仍只允许
合成身份与认证 loopback 端点；请求、总时限和重启不重置期限的门槛不变。

## 历史失败与本次可确认范围

CI `39894732783` 的崩溃后恢复用例曾返回 `stopped`，但当时的断言没有输出
具体停止原因，也没有保留该轮请求阶段与耗时。此历史根因仍为证据不足。
后来同一用例成功，或本机固定次数复现全部通过，都不能反推那次失败原因，
也不能证明偶发失败已消除。

本次只补失败诊断和确定性负例，不增加原 `request_seconds=0.2`，不重试
失败查询凑绿，不把严格同步超时改成成功，不重复发送已有意图的切换请求。

## 新留档字段

停止结果及原控制器 journal 的 `stopped.last_request` 现在保存最近一次
请求的 method、path、action、phase、stage、outcome、请求与剩余总预算、
实际耗时，以及已经取得的 HTTP 状态和响应字节数。不会保存 token、headers、
消息正文或完整 payload。该字段仅诊断，不参与准入判断。

`outcome=returned` 表示最近 HTTP 请求已返回；后续零门槛等本地检查仍可能
使控制器停止，不能将最近请求一概归为失败原因。`outcome=not_started` 表示
总预算检查未通过，尚未连接；它也不是已发生的网络超时。

## 组合回归

- 真实独立 fixture 进程完成 receiver 切换与回执同步后，以 `os._exit`
  退出；重启恢复只查询原 operation，未重新发送 receiver 切换。
- 在恢复查询里用事件握手保持请求未完成，让原 0.2 秒期限真实耗尽。
  控制器必须停止、保留同一 intent 和回执，sender 不切换；随后服务端
  完成查询也不能把已停止结果改为成功。客户端超时不证明服务端已停止。
- 恢复查询重确认回执时注入目录同步 EIO，即使最终文件已可见，也必须返回
  503 并停止；保留原字节、原 intent，不将可见文件当成已确认持久回执。

故障注入证明上述安全边界和诊断能够工作，不证明它们就是历史 CI 的原因。
压力、机器调度和存储延迟仍可能合法耗尽严格预算；如再发生，先读这一轮
原件定位，不提高预算、不重试或部署。
