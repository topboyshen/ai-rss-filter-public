# 周报关联历史查询的附加索引

## 已确认的问题与取证边界

`.122` 的一次真实周报请求在累计 5 秒预算到期时，正在执行关联历史
证据查询，SQLite 返回 `interrupted`，页面返回 503。该堆栈不能说明这条
SQL 单独用了 5 秒，也不能证明数据库锁、冷缓存或特定数据分布是原因。

隔离合成数据确认，原查询强制使用
`idx_event_evidence_event_time(event_id, announcement_at DESC)`，但实际筛选
的是 `mapping_id IS NULL` 和 `observed_at < cutoff`。该索引不能用于这两个
条件的范围查找；同一事件的大量映射证据或未来记录仍需逐条过滤，然后
按入库时间排序。这是可复现的无效扫描，不等于证明了生产故障的唯一根因。

## 本次修复

新增非唯一、局部性能索引：

```sql
CREATE INDEX idx_event_evidence_unbound_event_observed
ON event_evidence(event_id, observed_at, evidence_id)
WHERE mapping_id IS NULL;
```

周报关联历史查询改用此索引。公开证据过滤、按入库时间及证据 ID 排序、
成员分批顺序、共享历史条数上限、截断标记、分类和分页规则均不变。
`news_cache.link` 的索引查找保留，不扫描整个缓存来预先物化私有链接集合。

单成员分批直接利用索引顺序流式读取正文，在原有条数上限后再读取一条
溢出哨兵；哨兵不转换为卡片证据。不再先保存六万条身份、分批重读正文，
再做同一顺序的 Python 排序。多成员分批仍使用窄身份排序后读取正文，
不让宽文本进入临时排序；跨批优先级与共享上限不变。

整个报告仍共用原有 5 秒预算，不保证所有数据量或并发条件都能成功。

## 初始化与回退边界

- 正常 `init_db()` 在原有严格事件核心预检及初始化成功后安装附加索引。
- 不把新索引加入事件核心必需对象集合，不放宽旧表、索引或触发器校验。
- 已有同名对象必须定义正确；不以 `IF NOT EXISTS` 静默接受错误定义。
- 不修改新闻、信号、历史证据、迁移标记或评分文件；评分契约不因本修复改变。
- 旧版事件核心校验允许这个额外索引；代码回退不需要删索引，也不撤销数据。
- 直接对未完成初始化的旧库执行新查询会报缺少索引；读取路径不会偷偷建索引。

首次创建索引需要读取已有证据、增加磁盘占用并取得 SQLite 写锁；重复初始化
只校验已有定义。合成测试的建索引时间不能当作生产建索引耗时或锁等待上限。
若将来批准发布，需另行审阅启动时间、空间和锁影响；本 PR 不安装到生产。

## 验证口径

回归比较修复前后完整报告，包括更正、转载、合并组、缺失历史、分页和截断。
SQL 回归使用虚拟机步骤及查询计划验证无效扫描减少，避免依赖机器速度的
脆弱耗时断言。性能对照使用合成落盘库，不复制生产库、不调用模型。

六万条长历史另用冻结旧实现逐字段核对完整报告；该语义专用测试在内部
构建函数上不设截止时间，不能当作 5 秒性能通过。公开入口的预算另有回归。
原生性能中，测试库准备、索引安装、完整报告与额外 SQL 探针分阶段留证；
探针与完整报告各用独立进程，不把上一阶段仍持有的对象算作同等请求条件。
原先的超时和未完成场景仍保留，新结果不覆盖旧失败记录。

只有两边均成功的同输入才能宣称完整结果等价；旧版超时而新版成功时，
超时必须保留，不能把缺少的旧版输出当作等价证据。报告成功、调用成功
或一次隔离复现均不证明评分质量、全天稳定性或全部超时已经消除。
