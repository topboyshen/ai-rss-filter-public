# 新闻处理与模型调用关联

## 身份与范围

`process_entry` 每次执行生成独立的 `processing_id`，写入新增的
`news_processing_logs`。同一链接重试时执行编号不同，`article_key` 相同；文章键
复用账本的“链接＋评分契约”基础键算法，不改变账本身份。

现有 `llm_call_logs` 只增添 `processing_id`、`article_key` 两列。首评、语义修复、
格式兼容重试、后备及摘要调用继续使用原有 `request_id`、`attempt_kind`、
`response_mode`、`format_retry` 和 `usage_status`，不重复记一份用量。
调用关联使用执行上下文，不按接近的时间戳猜测。同链接单飞及不同链接并发的
调度策略不变；处理计时从取得同链接处理权后开始，不包含此前的等锁时间。

不经过 `process_entry` 的独立模型调用仍保留原日志，但没有文章身份。历史调用
不回填，不能据此追溯过去每条新闻的费用；本改动也不提供定时采集与 webhook
之间的完整历史入口成本拆分。不新增模型请求、采集、通知、重评分入口或页面。

## 执行来源与刷新轮次

新增诊断列记录实际执行入口，不按时间接近或批次完成数推断：

- `trigger_source=natural_continuation` 表示在刷新开场的续作调用中执行；
  `natural_feed` 表示刷新逐源处理；`webhook` 表示实际 webhook 任务处理。
  未显式标注的直接处理及历史行使用 `unknown`，不冒充已核实的来源。
- 每次真实刷新生成独立 `refresh_id`，同一次开场续作、逐源处理和
  `last_refresh_result` 共用该编号。它标识刷新执行，不单独证明 cron 调度成功；
  调度归因仍需结合实际 cron/worker 证据。webhook 不继承刷新编号。
  独立调用续作函数有实际续作入口，但没有可证明的刷新编号。
- `continuation_key`、`continuation_attempt` 读取当前处理实际锁定的 journal。
  记录的是处理结束时的持久次数，不是物理模型请求数。正常 feed 或 webhook
  命中既有 journal 时保留自己的实际入口，不会被改称开场续作。
  缓存复用不增加 journal 次数，也不冒充新模型调用。
- 首次递延的处理日志先于 journal 接收，故该次日志的续作字段仍为空；
  后续使用相同 `article_key` 关联，不能据此宣称首轮 journal 接收成功。

来源上下文按执行隔离，嵌套调用和异常退出后恢复，重启后从新执行入口记录，
不把旧刷新编号写入 journal 再继承。现有模型调用通过 `processing_id` 关联这些
诊断列，不重复存储 Token。缺处理记录时入口仍未知，不能把缺失日志当零费用。

## 最终处理结果不等于发布

每次执行记录原处理函数返回的原因、完成／延后／异常状态、实际 SDK 分派次数、
是否返回条目及复用类别。异常只记录类型，不记录异常正文。

- `cache`、`ledger`、`similarity` 分别表示对应路径复用；`score_cache` 表示评分器
  内存缓存命中，不保证整次处理零调用，其他阶段仍可能调用模型。
- `model_attempts=0` 表示该执行没有观察到 SDK 分派，不代表这条新闻从未花费 token。
- `signal_association=written_in_processing` 仅在本执行确实插入账本行、并在完成时
  按精确 `signal_key` 查到已提交的同链接、同契约行时使用。找不到提示的那一行
  不会改用另一条最新记录。
- `existing_at_completion` 只说明结束时存在同链接、同契约的账本记录；不声称由
  本次生成或其费用属于本次。异常和延后执行不借用已有信号冒充最终结果。
- `aggregation_selected` 是所关联账本行当时的入选标记，`result_returned` 是本次
  处理是否返回条目；两者都不能证明 RSS 输出、通知外发或首页可见。

## 有界只读查询与未知用量

`DB.get_news_processing_trace(processing_id, limit=200)` 只读返回一次处理结果和
最多 200 条已关联的现有调用日志。执行编号可由 `news_processing_logs` 中的
`article_key` 索引查找；同一文章多次执行应分开核对，再按需累计，不能只取末次。

返回结果包括 `processing`、`calls`、`found`、`calls_linked`、`truncated` 和
`usage`。没有最终记录时不编造结果，即使调用日志仍在。用量汇总仅覆盖返回的
调用行，`reported_*` 是已报告部分，不是完整账单或真实扣费。

完整、部分、未知用量分别计数；日志缺失、查询截断、读取不可用或缺最终记录
时不能宣称整次处理用量完整。未知用量不是零，成功请求也可能未返回用量；
失败响应已经报告的用量会保留。`processing_usage_complete` 仅表示本次记录的
调用均有完整用量并可对齐，不证明其他入口、历史调用或供应商账单已核对。

## 写入失败、迁移与发布边界

最终记录为最佳努力诊断写入，共用一次 200ms 的应用锁／SQLite 工作预算，
忙锁、写入失败或上下文初始化失败不替代评分结果或原异常。该预算约束可中断
的工作及锁等待，不是操作系统 I/O 的绝对耗时保证。诊断丢失时只记不含文章、
网址或凭证的警告。它仍增加同步上下文操作和一次小额写入，线上延迟与容量增长
尚未测量，不宣称零开销。

原关联迁移新增诊断表、索引及调用表两列；本次只给处理诊断表追加四列。
历史字段、缓存、不可变账本和 outbox 不回填、不改写。旧程序可继续使用原列
写入，新增来源默认 `unknown`、编号默认空、续作次数默认 NULL。新增记录不保存
文章标题、摘要、模型消息或原始回答，但会保存已有业务链接和 feed 地址，仍应
按私有业务数据保护。本 PR 不新增自动清理政策；与现有调用日志一样会持续增长，
后续保留期应单独审议，不能清理一侧后冒称关联完整。

评分提示词、阈值、校验、后备策略和缓存行为不改。本次修改的
`services/natural_scoring.py` 属于评分代码指纹清单，因此评分契约会变化。
合并不等于发布；
将来发布仍需单独接受新契约可能带来的旧链接重评与 token 风险。映射契约不改。
