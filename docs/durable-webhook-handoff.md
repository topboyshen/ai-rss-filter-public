# Webhook 持久交接 v1

本协议只证明消息保全与处理状态，不证明评分质量或通知已经送达。需要新应用镜像；不得改写或重新标记已构建的 `.126`。发送端事务 outbox 是独立补丁、独立镜像，两者均须另行批准发布。

## 接口与身份

- `POST /webhook` 保持 Miniflux 原始 HMAC-SHA256 签名验证。可靠交接必须同时满足 HTTP 202、顶层 `schema=1`、`durable=true`、`delivery_id` 与 `body_sha256` 都等于发送端保存的原始请求体 SHA256。普通 202 不足以交接。
- 可选 `X-AI-Filter-Delivery-ID` 必须等于原始请求体哈希。不用 URL 参数携带凭证。
- `POST /webhook/receipt` 重用**同一原始请求体及签名**，返回 200 的已同步回执。404 仅表示找不到回执，不证明消息从未执行；503 表示当前无法确认。请求上限、验签和接收接口相同，响应 `Cache-Control: no-store`，不返回新闻原文、任务正文或签名。
- 这个端点**不是只读 API**：确认过程可能建立私有目录、执行 `fsync`、恢复完整 `.pending` 或重建任务索引。它不新建评分任务、不调用模型，不等于不写盘。严格只读授权下只能使用已冻结证据或另行批准的只读取证，不能把调用此端点包装成只读检查。
- 原始消息身份与规范化任务身份分开：不同原始体可以经 feed 别名规范化后绑定同一 `task_digest`，但每条回执的 `delivery_id`/`body_sha256` 仍属于其自己的请求体。`primary_delivery_id` 引用任务主回执，分类结果不受影响。
- `accepted_strategy`/`accepted_revision` 是首次接收的审计身份。缺失构建 revision 明示 `unknown`，不猜测。已经接受的同一消息不会因为版本变化自动新建任务；执行前策略不匹配则保留任务，不跨契约静默评分。

## 落盘和恢复顺序

同一现有 spool 文件锁覆盖容量判断、去重和状态转移：

1. 同步包含原始消息恢复上下文的队列文件、所在目录；
2. 同步独立原始消息回执与任务索引；
3. 才返回带持久回执的 202。

不再用内存重复标记提前返回成功。文件可见但同步失败仍是不确认；重复交付和查询必须重新确认文件与目录同步屏障。队列已写、回执尚未写时，worker 必须先补齐回执才可执行。失败任务保留，不阻塞可正常领取的其他任务。

完成时先保存独立完成回执，再删除队列并同步其实际父目录。领取和过期租约恢复先检查独立完成回执，避免完成后删除中断导致再次执行。普通内部后台命令与旧队列仍用原有完成账本，但同步失败不再被吞掉。终止未评分保留为 `terminal`，绝不写作 `completed`；原有负收据和归档意图继续保留。

`state=accepted` 表示系统持有可恢复消息，不表示当前仍在等待；`state=completed` 表示整个批次处理游标到末尾且无终止未评分；`state=terminal` 表示未完整处理的终态。完成详情包含游标、总条数、通过/过滤计数、终止条数与队列尝试数，不替代逐新闻信号账本。源内容无效被过滤也属于已处理，并不表示产生有效信号。

## 容量、权限与拒收保全

- 回执目录 `webhook_spool/receipts/` 与索引目录 0700，文件 0600，要求当前进程所有权、普通单链接文件，拒绝符号链接。只保存新闻原始体，不保存 HMAC 密钥或签名。
- 硬上限 4096 条回执、256 MiB **预留容量**，不是可用磁盘保证。每条预留原子更新临时副本、有限完成详情及主索引空间，容量可调低、不能调高；16 KiB 完成详情上限。队列仍最多 128 个活跃任务，请求仍受现有 HTTP 大小上限约束。
- 单份回执另有 8 MiB 编码文件硬上限，限制大文件读取及 JSON 解码的内存暴露；不把全库 256 MiB 当作单文件读取缓冲。默认 1 MiB HTTP 请求仍须通过真实路径回归；若人为调高请求上限、使回执超过 8 MiB，则拒绝确认，原队列和发送端原件继续保留，不能以普通 202 代替持久回执。
- 不按时间自动删除回执或未交接原件；因此长期运行需要单独批准的归档/容量治理。容量满、权限不符、磁盘满、同步失败或身份冲突不确认交接；发送端必须保留原始体和重试状态。接收端不能保全根本未到达或被它拒收的消息。
- 新消息的容量校验仍可能在全局 spool 锁内逐条校验已有回执；原生 AMD64 隔离容量对照见 `Webhook native capacity` 的对应提交产物。该测试使用合成回执及镜像内真实 Flask 接收路径，不等于 Gunicorn/网络端到端吞吐测试，不承诺毫秒级、零开销或生产高负载时不超时。
- 无法确认的临时写入保留为证据；不能推定为成功。损坏的原件需要人工审定恢复，不能静默覆盖或用新的正文冒充旧消息。
- 残缺回执只在能够从已校验的主回执或严格同步的原队列上下文证明消息/任务归属时，按原完整预留量计作隔离占用；原件不删除、不覆盖。对应消息和同任务别名仍拒绝确认或执行，但不阻塞无关的新任务。无法证明归属、身份冲突、权限异常或孤立残缺件仍保守拒收，不能靠跳过校验恢复服务。
- 新别名先在私有 `receipts/alias-intents/` 写入不可变接受意图，保存原始体、首次接受时间及已核验主回执身份；文件和目录同步后才写普通别名回执。只有普通回执也完成同步才可返回可靠 202。重复交付使用原意图时间，不生成新时间、不产生另一评分任务；已完成或终止的主任务不会重评。对外回执 schema 不变，内部新别名以 `alias_intent_schema=1` 区分，既有完整回执仍可读。
- 新别名意图自身首次写入中断时，仅在同 ID 普通回执 final/pending 都不存在、意图只有 `.pending`、私有文件安全及同步屏障均通过的条件下，保留原件并隔离。它不证明接受，也不提供任务身份；同 ID 接收/查询仍 503。不同消息可在剩余容量足够时继续。意图完整后必须核原始体哈希、任务、主回执和索引、策略与 revision，再严格同步，才能采用实际预留量。
- 别名首次写意图前临时要求 `3 × (8 MiB + 16 KiB + 2048)` 的最坏槽位余量（约24.05 MiB），不是提高256 MiB上限。残缺意图保持该最大占用；完整新别名的实际预留包含意图、普通回执和更新临时副本。意图与普通回执按同一 delivery 合并计条数/预留，4096条硬上限不变。因此接近容量上限时小别名也可能提前拒收；已确认消息的重复交付和查询不因此新占槽。不自动清理意图或失败证据。
- 旧版本已留下且没有独立接受意图的残缺别名，不能从损坏头部猜测原始体、接受时间或伪造新证明；仍保守拒收，须单独人工审定。孤立未知格式、权限/身份冲突、损坏 final 或同步仍失败不适用隔离豁免。本修复保证新协议写入路径的可归属隔离，不声称修复任意历史损坏。
- 残缺的完成/终态写入不允许退回 `accepted` 再次执行。文件读取按实际文件大小有界分配，并检查读取前后身份及大小；256 MiB 是整个回执目录的容量上限，不是每次小文件读取应分配的缓冲。
- 原有非终态死信的有界清理不再是新协议原始消息的唯一副本；独立回执保留精确原始体及规范化任务。终止负收据仍不自动清理。

## 发布、兼容和证据限制

新增回执不是评分算法或评分缓存；本 PR 不改提示词、事实/数值保护、评分阈值、模型重试预算。需复算评分指纹确认，不能把“指纹未变”说成“调用量不会变”：恢复之前丢失的消息可能增加正常调用。

旧版本完成账本只有摘要和时间，不能追溯生成可靠回执；遇到同任务的旧未签收队列/旧完成记录时拒绝给出新协议的成功证明，等待独立人工核对。旧格式内部任务继续可读，但其原始交付未获本协议证明。

旧 `.126`/`.125` 不认识新的持久回执及完成恢复语义。回退前必须停流、静止生产者消费者，独立保全原始消息、回执、队列、终态与负收据，核对未完成和删除未确认状态；不能仅替换镜像继续旧 worker。新发送端在旧接收端只给普通 202 时应保留消息，不能降级为已交接。不要同时运行旧、新发送线程，也不自动补发历史批次。

测试使用临时文件系统、假模型与故障注入；进程重启不等于断电测试。文件系统、磁盘控制器、Docker 卷的真实断电耐久性不由单元测试证明。此 PR 不部署，不读取/复制生产数据库、不触发采集、不调用真实模型、不清理历史证据。

## 原生容量对照范围

`scripts/verify_webhook_capacity_native.py` 只允许本机 Linux AMD64 与本机 Docker daemon，拒绝 ARM/macOS 模拟执行；从完整提交构建独立随机标签，不使用或修改 `.126`。每个测试容器固定 768 MiB／256 PID、1 CPU、只读根文件系统和无网络，以同资源对照冻结旧提交与候选。旧提交不预设必须 OOM，候选的任何失败、超时、OOM、缺结果或身份/资源不符均不能通过。

对照包括小文件分配、0/1024/4095/4096 条、超过 99% 字节预留容量、默认最大请求、残缺件隔离及新进程恢复、受限 tmpfs 的真实 ENOSPC，以及别名残缺/并发/重启、别名容量、意图同步失败和1024条同任务别名库存。预置库存通过实际编码/校验/同步写入构造，只在预置阶段跳过逐次准入扫描，不冒充历史 HTTP 交付。安全输出及小范围合成故障原件由 CI 产物保留 14 天；此前本地失败证据不覆盖。

### 固定镜像联合证据（2026-10-22）

历史开发中的原生 Linux AMD64 联合验证材料保留在私有档案，不随公开仓库分发。公开版本的兼容性与资源验收须重新绑定本仓库提交、候选镜像及实际 CI 结果，不能把旧私有验收当作新版本通过。

- 接收端固定 768 MiB／256 PID／1 CPU，私有卷和独立 internal 网络，无真实模型、自然采集或评分 worker。普通 202 导致 `held`，没有自动解除；下游已接受但 ACK 丢失按原文自然重试，签名回执与任务身份一致。
- 预置 1024 条同任务别名后，一条真实 sender→Gunicorn 请求在代理记录区间为 4.517 秒。不是完整 sender 尾延迟、并发吞吐或最坏容量保证；不能据此保证生产不会超过发送端 10 秒超时。
- 所捕获接收端 cgroup 峰值最大约 132.04 MiB，并无捕获 OOM；不是全时段精确峰值，也不是发送端／PostgreSQL 的峰值。
- 私有卷接收端重启、进程 SIGKILL 恢复、发送端自然 lease 恢复有证据。16 MiB tmpfs 的实际 ENOSPC 拒收与恢复也有证据，但不是物理磁盘或 PostgreSQL 满盘；tmpfs 停止后只保留已导出的原始安全快照。
- 联合中的“切换”只是同镜像、同契约接收端替换；不证明旧 `.125`／`.126` 回退或生产全部入口已静止。合成 completed 不是实际评分成功。实际全入口受控切换仍要独立验证和批准。

## 容量／留存与有界试运行方案

当前协议**不支持无限期启用的容量闭环**。回执、任务索引和 alias intent 均不自动过期；完成或终态也仍计占用。单纯将原件复制到离线归档不会释放在线容量；删除在线回执／索引会破坏重复交付与完成保护。因此本方案不提供清理脚本，不以“已备份”替代幂等保留。持久化全量留存与既定 `NO_BACKUP` 政策也不能混称已有恢复保证。

启用前应形成一份人工批准的**有限时间、有限新增 delivery 数**计划，并把以下信息绑定到同一固定版本和新鲜快照：

1. 当前 primary/alias/held/无法归属槽位的合并条数和完整 reservation、活动队列数、权限及同步证据；不只数 `*.json` 或磁盘 `du`。已有 `.pending` 与 intent 要按存储规则计费，不能漏算或双计。
2. 预计高峰新增 primary 与 alias 速率、样本来源、平均 reservation 只供估计；另列可被控制器实际约束的新增条数和最坏 reservation。重复投递同原文不算新 delivery，新的 raw alias 算一条；试运行中欲释放的旧 sender backlog 也包含在新增预算内。
3. 发送端还需单独核5000条／256 MiB、原文、签名、endpoint、保留年龄、剩余尝试数与 `held`。接收端预算通过不能替发送端预留空间；sender `acked` 至少保留7天，本接收端没有7天自动清理。
4. 负责人、观察间隔、明确停止接收新任务的动作和恢复授权；仅报警或脚本算出预算，不等于有可用的启停控制器。达到时间／条数上限、同步错误、身份变化、无法归属状态或审批所列停止条件时，应停新增接收并保全在途消息，不删除、不重签、不补发。

**本方案建议阈值，不是运行时配置改动：** 占用或保守投影到80%进入警戒、到90%建议停止新试运行；4096条／256 MiB／128活动任务硬上限完全不变。新 alias 另保留约24.05 MiB首次意图槽位。出现 `held`／未知状态先单独审定，不能通过提高预算、延长试运行或手动释放“过关”。本方案没有获准自动停机；实际启停由后续单独审定控制器执行。

### 纯离线规划工具

`scripts/plan_webhook_receipt_trial.py` 只读一份本地冻结 JSON，最多64 KiB；无 SSH、HTTP、Docker、模型或生产路径访问，不调用有恢复写的 receipt API。输入中的已核验标志与证据哈希是调用者声明，工具不把它们当成亲自核实了现场。`--as-of` 是重放规划参考时间，不能伪称实际观测时间。

工具建议的单次窗口最多120分钟，快照距参考时间不超过300秒，观察间隔最多60秒；这些均为**离线方案边界**，不修改应用 runtime。以硬单记录界限保守预算每条 primary、每条 alias，包括临时副本与完成预留，不用平均大小替代最坏预算；因此可接受的试运行可能很小。不能为了容纳真实高流量而静默调低这个上界；需另有可验证、被执行器约束的消息大小／总量方案再审定。

### 切换、拒收及回退协同

短时窗口仍须由经过隔离验证的适配器证明**全部**旧生产者与消费者及在途请求已静止；不能用一个buffer暂停标志代替全部停流。旧契约未完成续作不为零、老接收端只给普通202、原消息或交付归属缺失时停止，不自动降级。拒收未持久入sender事务的新闻可能滑出上游列表，不能称已保证无损。

新旧 sender 不得并行交付同批消息。新 sender 的普通202／错误回执产生held，不会因服务恢复自动放行；补偿须以精确原文、原签名、endpoint、delivery/task/contract逐条核对，禁止重构消息或重签跨契约。切换后的新消息在新协议下确认不等于旧held已经闭环。

回退是另一次受控操作，必须先静止并保全PG outbox、queue、receipt、alias-intent、task index、continuation journal、负收据和终态原件。旧Miniflux读得了schema132不等于消费新outbox；旧receiver读得了普通queue不等于认识新完成保护。存在新协议未完成／unknown状态或跨契约任务时不能直接切回。原 `.125`、原Compose、终态证据和既有 `.126` 均保留；关闭自动回退，不降低schema、不删索引、不清日志、不补跑采集。
